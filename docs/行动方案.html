1一页看懂

读者：所有人

第一版做什么
  • 在微信里用一句话记下时间或开销。
  • AI 把这句话拆成结构化记录：开始时间、结束时间、分类、金额。
  • 机器人回复一条确认，可以撤销。
  • 网站显示今天、本周、本月的时间分布和开销。
第一版不做什么
  • 首期不录音、不接Whoop。本轮推进P3身体面板；录音仍在P4。
  • 只服务子民一个人，不做多用户。
  • 不频繁主动提醒。微信机器人主动发消息的额度很少。
  • 不采集新音频或图片；保留本机历史附件。
三条不可违背的原则
  1. 原话先落库，永不丢。每条消息先原样存进数据库，再交给 AI 解析。AI 失败了，可以从原话重新解析。
  2. Supabase 是唯一真源。网站、本机 LifeOS、以后的记忆系统都从 Supabase 读数据，不再各存一份。
  3. 大脑可替换。模型通过 Parser 接口接入；当前使用官方 CLI，业务契约与模型实现分离。

2使用说明

读者：用户

2.1 第一次使用

  1. 员工部署完成后，会在 VPS 上生成一个二维码。用你的微信扫码并确认。
  2. 微信里会出现一个机器人对话框。先给它发一句"你好"，激活对话。
  3. 完整传话筒上线后，每句话先落库。v1.7 开始部署原话入库与 CLI 解析；以部署记录中的运行状态为准。

2.2 怎么说

像发微信给助理一样说话就行，不需要固定格式。现在以收到消息的北京时间为准；明确钟点优先，只有时长时只问一个起止锚点。

2.5 查看面板

  1. 打开网站地址（见第 10 节）。
  2. 输入本人密码，再输入手机验证器的 6 位动态码。
  3. 首次进入时设置本人密码，再扫码绑定验证器。

2.6 注意

  • 发语音时，请先用微信的"转文字"。系统只能读到微信转出来的文字。
  • 可以直接提问和追问。初始“收到，正在处理”是处理中确认，随后发送回答或账目回执；失败时说明原话保留并延期重试。
  • 不要在消息里写别人的隐私信息，比如身份证号或病情。

3运行逻辑

读者：员工、AI

系统由四个部件组成：微信官方通道、VPS 上的传话筒、Supabase、网站。传话筒只主动向外建立连接，所以 VPS 不需要开放任何对外端口。

编号对应 3.1 节的步骤。虚线框内的两个部件都运行在 VPS 上。

3.1 一条消息的完整旅程

示例消息："午饭 38，微信付的"，13:05 发出。

  1. ① 发送。子民在微信里把消息发给机器人。
  2. ② 接收。传话筒通过 iLink 长轮询收到消息，校验发送者是子民本人。不是本人 → 丢弃，不回复，记一条日志。
  3. ③ 存原话。写入 raw_inputs，状态记为 pending。用微信消息 ID 做唯一键，同一条消息重复到达只存一次。全批原话入库成功后，才推进微信游标。普通记录同时排入“已存原话，正在整理”的确认回执。
  4. ④ 解析。传话筒把原话、接收时间、分类、独立补充及真实账户和进行中活动交给 Parser。管家常驻规则生成受限工具计划；重试仍使用原话接收时间。
  5. ⑤ 校验。传话筒用 schema 校验 JSON。不合格 → 重试一次 → 仍不合格：状态记为 failed，回复"已存原话，稍后整理"，流程结束。
  6. ⑥ 写记录。写入 transactions（或 time_entries），关联原话 ID。原话状态改为 parsed。两本账与状态在同一数据库事务中提交。
  7. ⑦ 回执。传话筒读取已提交账目拼出回执，先持久化再发回微信。发送失败按退避时间重试，同一回执使用固定 client_id。回执由程序拼接，不由 AI 生成，保证回执和数据库内容一致。
  8. ⑧ 显示。子民打开网站，网站按 RLS 规则读取 Supabase，显示这条记录。

3.2 原话的状态

状态含义下一步
pending已存原话，等待解析解析成功 → parsed；失败 → failed
awaiting_clarification缺少必要信息，已发追问仅同来源30分钟内、题型一致的短答关联补充；新活动、提问和控制指令独立执行
parsed已生成结构化记录终态。撤销只标记记录，不改这个状态
failed解析失败（额度用完、超时、格式错误）每 10 分钟自动重试；累计 5 次后停止重试，等人工处理
ignored独立补充或旧版无账目输入终态；新版闲聊与情绪标记存档后为parsed

3.3 定时任务

时间任务阶段
每 10 分钟重试 failed 状态、尝试次数小于 5 的原话。成功后补发回执P1
每天 02:00pg_dump 导出数据库 → age 加密 → 上传 R2，保留最近 30 份P1
每天 23:30推送当日小结：时间分类汇总、总支出、未记录的时间段。每天只发一条，不占用太多主动消息额度P2

4.1 全局约定

主题约定

金额整数，单位为"分"（amount_cents）。禁止用浮点数

4.2 模型与 Antigravity CLI 使用边界

v1.7 决策：子民明确要求微信调用已授权的官方 CLI，不使用 API Key。运行用户为 lifeos，模型为 gemini-3.8-flash-low。官方 FAQ 对个人订阅的应用封装支持边界仍有效；本决策不代表平台给予额外授权。

  • 调用官方 agy -p，使用参数数组，不经过 shell。不读取或复制 OAuth 凭据。
  • 工作区固定为 /var/lib/lifeos/parser-workspace。CLI 不接收数据库和微信密钥。
  • 仅接受裸 JSON 或完整 JSON 代码块，空响应单独分类；所有结果仍经原 schema 校验，不从解释中截取对象。
  • 同一时间只运行一个 CLI；JSON 格式错误附纠正提示补试一次，原始接收时间保持不变。超时或额度错误延期十分钟，累计五次停止。
  • CLI 1.4.7 的复杂 --json-schema 实测返回空结果，当前把 schema 放入提示。CLI 输出先通过 zod，再提交事务。v1.8 在相同 Gemini 3.8 Flash 内改用 Low 档；七条真实样例通过，降低结构化提取的等待。模型不直接写库，也不生成回执。
  • 安装、账号授权、真实结构化解析和业务收发分别验收。未通过的项目写入部署记录。

5.1 事务与恢复

  • ingest_input 幂等保存原话。claim_next_input 领取三分钟租约。
  • apply_parse 原子写入两本账并改变原话状态。失败全部回滚。
  • run_command 原子执行撤销、今天、帮助。同一指令重投不重复撤销。
  • 符合题型的短答关联原始追问；新活动和提问不被旧问题接管。“停止计时”直接封口，“取消追问”退出等待；原话始终保留。
  • 回执从已提交账目生成。回执持久化后由独立任务发送，模型等待不阻塞原话确认，失败最多重试五次。

5.2 权限与视图

  • 匿名无权读写。本人 JWT 必须为 aal2。客户端底表只读；人工编辑通过限定字段的事务 RPC。
  • 前端不能读取微信 payload 或投递上下文。人工编辑通过 Worker 调用 edit_record，不开放解析和投递 RPC。
  • service_role 仅存 VPS 私有配置；原话不可变触发器仍然生效。
  • v_daily_time 按上海午夜拆分跨日净时长，保留扣减与进行中时段。v_daily_money 分币种汇总收支，排除转账。
  • v_records 统一时间、流水和本机辅助记录的分页查询；不暴露微信 payload。
  • 视图使用 security_invoker 继承底表 RLS。生产关闭公开注册。

本机三库历史已一次性迁入；网页编辑写入云端，不建立旧版本机双向同步。后续 Whoop、录音与记忆表按阶段另写迁移。

读者：员工、AI

6.1 传话筒（apps/relay）

main.ts 组装通道、解析器与仓储。业务依赖 contracts.ts 接口。

文件职责

6.2 解析契约（Parser 的输入和输出）

这是整个系统最关键的接口。无论换成哪个模型，输入和输出都必须保持一致。

常驻元提示词真源：apps/relay/prompts/parse.md。部署到工作区 AGENTS.md，启动检查逐字一致；每次调用同时注入同一规则。完整语义与工具落点见 管家元提示词.md。

职责：保存每句话，直接回答普通问题与追问。模型输出受限计划，由 apply_steward 校验并持久化。明确要求执行上一轮活动时，可引用最近八轮中本人原话的钟点和活动；资金账户与金额仍只取当前原话及明确补充。不给模型数据库凭据。

时钟冻结到 received_at。只给时长而无起止锚点时追问；分类不追问。资金账户必须存在并由原话或补充明确指定，支付渠道单独保存。普通支付不切换活动。仅记人民币；转账、精确纠错和历史范围查询走网页。

输出 schema（apps/relay/src/parser/schema.ts 的权威版本）：

{
  "time_entries": [
    { "start_at": "2026-10-24T12:40:00+08:00",
      "end_at":   "2026-10-24T14:00:00+08:00",
      "category": "work_1",
      "activity": "写方案" }
  ],
  "transactions": [
    { "occurred_at": "2026-10-24T13:05:00+08:00",
      "direction": "expense",
      "amount_cents": 3800,
      "currency": "CNY",
      "category": "food",
      "account": "wechat_pay",
      "funding_account": "生活账户",
      "merchant": null,
      "note": "午饭" }
  ],
  "time_events": [],
  "archive_kind": null,
  "unsupported": null,
  "clarify": null,
  "answer": null
}

time_events 最多一个 {action, at, category, activity, note}。连续多个边界用闭合时段加最后一个switch。事务先在首段起点闭旧计时，再校验并写入；明确活动直接执行。stop按实际结束点封口，不因超过24小时拒绝；同分钟停止保留真实秒数。真实已结束记录冲突或网页并发变更仍回滚。

archive_kind 为 inspiration、diary、emotion 或 raw。标签写入 raw_inputs.parse_result，正文仍是不可变原话。云端尚未连接本机 Obsidian，不声称已写入任何笔记文件。unsupported 表示原话已保留，但操作尚需网页或后续接入。

传话筒根据输出决定下一步：

  • 三个写入数组有内容 → 校验租约、账户和活动状态，在同一事务提交，从数据库快照回执。
  • answer有内容 → 持久化后发送自然回答，最多3000字；不能用“已存原话”替代回答。
  • clarify 有内容 → 三个数组为空且answer为null。补充原话独立保存，冻结原接收时间后重新解析。
  • 仅原话标签或未接入操作，且没有answer → 状态记为 parsed，说明存档位置和边界。
  • 90秒内同账户、金额、方向和事由重复 → 确认确为另一笔后才新增。重放同一 input_id 永不重复。
  • 撤销活动切换 → 软删新段并按修改版本恢复因果前驱。原话不删除；后续改动过的前驱不自动恢复。

7安全设计

读者：员工、AI

目标：公开登录页不含私人数据。只拿到密码时，服务端与数据库均拒绝读取记录。

层机制挡住什么
0 · 会话Pages Worker：同源请求、HttpOnly Cookie、禁用私密响应缓存跨站请求与令牌泄露
1 · 密码Supabase Auth 密码，至少 20 位，保存在密码管理器里只拿到你设备的人
2 · 动态码Supabase 原生 TOTP MFA；RLS 要求会话等级为 aal2密码泄露
3 · 本人边界Worker 验证本人 ID；RLS 再次验证归属及 AAL2越权读取

7.1 密钥存放

密钥存放位置说明
SUPABASE_SERVICE_ROLE_KEYVPS：/etc/lifeos/relay.env（权限 600）最高权限。只能放在这里
SUPABASE_PUBLISHABLE_KEYCloudflare Pages 环境变量公开也无妨，有 RLS 保护
Antigravity CLI 登录凭证VPS：lifeos 用户主目录下的官方凭据存储本人通过官方 OAuth 登录；目录以安装版本为准，不输出凭据内容
iLink 会话VPS：传话筒的数据目录子民扫码生成
备份加密公钥VPS只能加密，不能解密
备份解密私钥子民离线保管（打印 + 密码管理器）不放在任何服务器上

  • SSH 沿用已验证的 root 密钥入口。验证替代管理账号后再收紧权限，禁止直接关闭唯一运维入口。
